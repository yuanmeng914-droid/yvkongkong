# AI 长期记忆闭环设计

## 目标

在现有“AI 看看今天”基础上完成两个能力：每日分析可以引用当前用户已经确认保存的长期记忆；模型发现可能值得保留的新模式时，只生成候选记忆，必须由用户确认后才写入现有 `user_memories` 表。

## 范围与稳定性边界

- 不修改任务新增、编辑、删除、完成、顺延、重复与同步逻辑。
- 不修改登录、天气、重要日子、心情、复盘、PWA、Service Worker、推送和部署配置。
- 不新增数据库表，不修改 `user_memories` 表结构或 RLS。
- 不引入 Embedding、pgvector、RAG、向量数据库或新的 Agent。
- 不自动发布线上版本。

## 服务端数据流

Growth Agent 继续验证当前 Supabase 登录会话，并通过带有用户 Authorization 的 Supabase Client 查询数据。每日分析先按现有逻辑读取缓存：普通进入页面时返回缓存；只有前端传入 `force: true` 的“重新看看今天”请求才重新读取当天数据和最新长期记忆并调用模型。

长期记忆只读取 `deleted_at is null` 的当前用户数据。第一版最多提供 8 条，类别优先级为：`goal`、`habit`、`observation`、`experience`、`preference`；同类别按 `updated_at` 降序。传给模型的字段仅包含 `id`、`type`、`content`。

## 结构化模型输出

模型仍返回三个现有字段：

- `summary`
- `observation`
- `tomorrow_suggestion`

同时返回：

- `referenced_memory_ids`: 实际使用的记忆 ID 数组。
- `memory_candidate`: `null` 或 `{ type, content, reason }`。

服务端不信任模型返回的记忆正文。它只接受传入记忆集合内的 ID，并由服务端使用原始数据库记录组装前端响应中的 `referenced_memories`。候选类别只能是现有五类，内容和原因都必须是非空短文本。

## 候选记忆去重

第一版采用确定性文本规范化：去除空白、常见标点并转为小写后比较。与任一现有记忆规范化内容完全相同，或一方完整包含另一方且较短文本达到合理长度时，候选视为重复并返回 `null`。不引入向量检索。

## 前端交互

AI 结果下方增加两个独立区域：

1. 引用记忆区：显示“本次参考了 N 条关于你的记录”，用户可以展开查看分类与原文。
2. 候选记忆区：显示候选内容和原因，提供“记住”“编辑后记住”“先不用”。

“记住”直接调用现有前端记忆保存业务；“编辑后记住”复用现有记忆编辑弹窗并预填候选；“先不用”只隐藏当前候选，不写数据库。无论哪种情况，模型都没有数据库写权限。

保存前，前端再次对当前本地有效记忆做规范化去重。若重复则不新增并提示用户。成功保存的候选 `source` 使用 `ai`，用户手动创建的记忆继续使用 `user`。

## 缓存语义

- 普通打开成长记录页：展示已保存的当天分析及其引用与候选信息。
- 首次点击“AI 看看今天”：当天没有缓存时生成。
- 点击“重新看看今天”：发送 `force: true`，重新读取最新记忆并覆盖当天缓存。
- 新增或编辑记忆本身不会自动触发模型调用。

为使缓存完整复原，需要在 `ai_daily_insights` 已有 `source_snapshot` JSON 中保存分析使用的引用与候选结构；如果现有表没有专门响应字段，读取缓存时从该 JSON 中恢复，不新增列。

## 隐私与错误处理

- 查询依赖现有 RLS，只能读取当前用户记录。
- 日志不打印记忆正文、Prompt 或模型密钥。
- 记忆读取失败时返回现有数据存储错误，不在缺失记忆的情况下假装生成长期观察。
- 模型返回不存在的记忆 ID 时忽略该 ID。
- 非法候选、重复候选或数据不足时不展示候选。

## 测试与验收

- 单元测试覆盖筛选顺序和数量限制、结构校验、引用 ID 白名单、候选去重。
- UI 结构测试覆盖引用区、候选区和三个用户动作。
- 服务端测试确认不把任务标题或未筛选数据加入上下文。
- 回归测试覆盖现有首页、成长记录、记忆、天气、重要日子与 PWA 结构。
- 运行 `node --test`、`node --check app.js`、`node --check sw.js`、`git diff --check`。
